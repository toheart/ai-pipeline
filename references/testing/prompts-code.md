# 代码类测试提示词模板

适用场景：面对具体代码进行可测试性评估、单元测试设计、测试框架设计。

---

## 1. 代码可测试性评估 + 单元测试设计

合并原文 #7（可测试性检查）和 #8（单元测试设计），因为两者通常是连续动作：先评估再设计。

### 输入参数

- `code`：待评估的源代码
- `language`：编程语言和框架
- `test_framework`：（可选）已有的测试框架（如 testify、Jest、Vitest）

### 输出要求

**Part A：可测试性评估**

1. 领域逻辑和外部依赖是否混在一起
2. 哪些逻辑应抽成纯函数或领域对象
3. 哪些依赖需要抽象成接口
4. 当前代码为什么难测（如果难测）
5. 重构建议（提高测试 ROI）

**Part B：单元测试设计**

1. 需要测试的核心业务规则
2. 正常场景、边界场景、异常场景
3. 参数化测试数据
4. 需要 Mock 的依赖
5. 不应该在单元测试中测试的内容（应下沉到集成/API 层）
6. 测试命名建议
7. 测试代码示例
8. **断言来源分类**（每条断言必须标注来源）

> 重点覆盖业务风险，不要只追求覆盖率。

**Part C：断言来源验证**

为每个被测函数的每条断言标注来源类型，优先级由高到低：

| 来源层级 | 说明 | 可信度 | 示例 |
|---|---|---|---|
| L1 业务契约 | 来自需求文档、用户故事、验收标准 | 高 | "进度百分比 = 已完成数 / 总数 × 100" |
| L2 API 契约 | 来自接口定义、OpenAPI、Proto、枚举映射 | 高 | "status=3 对应 '已取消'" |
| L3 共享常量 | 前后端共享的枚举、状态码、错误码 | 中 | "CheckingState.PASS = 1" |
| L4 代码推导 | 仅从当前代码实现推断 | 低 | "这个 if 分支返回 null" |

编写规则：

- L1-L3 来源的断言直接写，它们是**业务防护网**
- L4 来源的断言在测试注释中标注 `// 断言来自代码推导，需业务确认`
- 如果一个函数所有断言均为 L4，暂停编码，先向用户确认业务意图
- 避免"复述代码"式断言——如果源码改了断言就得跟着改，说明断言缺乏独立业务依据

示例对比：

```javascript
// 差：复述代码，没有独立业务意义
expect(result.progress).toBe(Math.round((2 / 5) * 100))

// 好：L1 业务契约——进度 = 已完成 / 总数
expect(result.progress).toBe(40)
```

```go
// 差：复述代码逻辑
assert.Equal(t, "已取消", label)

// 好：L2 API 契约——后端 status=3 的展示文案是"已取消"
assert.Equal(t, "已取消", getStatusLabel(3))
```

## 2. API 自动化测试框架设计

原文 #9。适用于为项目搭建系统性的 API 测试基础设施。

### 输入参数

- `tech_stack`：后端技术栈（语言、框架、数据库、中间件）
- `api_style`：接口风格（REST / GraphQL / gRPC）
- `auth_method`：认证方式（JWT / Session / OAuth / API Key）
- `existing_tests`：（可选）已有的测试基础设施描述

### 输出要求

1. 目录结构
2. 环境配置管理方案
3. HTTP Client 封装（认证、Header、Token 统一处理）
4. 请求/响应日志记录
5. 断言能力设计
6. 测试数据外置和参数化方案
7. setup / teardown 方案
8. Mock / Stub 接入方式
9. CI 接入方案
10. 失败后快速定位方案
11. 报告生成方案
12. 每项的设计理由
