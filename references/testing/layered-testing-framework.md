## 核心理念

测试是**风险控制系统**，不是用例堆砌。研发视角下测试解决四件事：

1. **找风险**：哪里最可能出问题
2. **控风险**：用什么测试手段覆盖
3. **降成本**：放在哪一层最划算
4. **建信心**：结果是否可信、能否支撑发布

关键词：风险、反馈、成本、可信性、可维护性、ROI。

## 9 层测试模型

```
┌─────────────────────────┐
│   9. 生产巡检 / 右移测试   │  ← 线上真实验证
├─────────────────────────┤
│   8. 验收测试              │  ← 业务视角
├─────────────────────────┤
│   7. UI / E2E 测试        │  ← 用户真实操作
├─────────────────────────┤
│   6. 皮下测试              │  ← API 串联完整业务流
├─────────────────────────┤
│   5. API / 接口测试        │  ← 接口正确性
├─────────────────────────┤
│   4. 契约测试              │  ← 上下游一致性
├─────────────────────────┤
│   3. 集成测试              │  ← 服务与依赖协作
├─────────────────────────┤
│   2. 组件 / 模块测试       │  ← 模块内协作
├─────────────────────────┤
│   1. 单元测试              │  ← 函数/类/规则
└─────────────────────────┘
```

## 分层总览表

| 层 | 测什么 | 优点 | 缺点 | 使用建议 |
|---|---|---|---|---|
| **单元测试** | 算法、计算、状态机、参数校验、边界条件、业务规则 | 最快、最稳、最便宜、定位精确 | 不能证明服务间协作、不能验证真实依赖 | 复杂业务逻辑优先下沉到此层。难写通常说明代码设计边界不清 |
| **组件/模块测试** | 前端组件状态、后端 Service 层组合逻辑、模块内多类协作 | 比单元更接近真实行为、比集成更轻 | — | 模块内逻辑复杂但无需拉起整个系统时使用 |
| **集成测试** | 数据库读写、缓存、消息发送、第三方调用、事务、配置加载 | 验证真实依赖、发现单元测试发现不了的问题 | 比单元慢、数据准备复杂、环境依赖强 | 可控依赖用真实实例，不可控依赖用 Mock。核心抓手：Happy Path |
| **契约测试** | REST/RPC/消息队列的字段类型、状态码、错误码、枚举、向后兼容性 | 提前发现接口不兼容、降低联调成本 | 需要团队契约意识和契约文件维护 | 接口变化频繁、上下游团队不同时优先考虑。防止"说好的接口变了" |
| **API/接口测试** | 接口正确性、参数校验、权限、错误码、幂等性、分页排序过滤 | 比 UI 稳定、接近业务、适合 CI 自动化回归 | 不能验证 UI 展示、跨服务链路长时变重 | 后端自动化回归的主力 |
| **皮下测试** | 准端到端业务流、跨服务链路、后端完整流程 | 比 UI E2E 快、ROI 很高 | 不能验证 UI 交互和展示 | E2E 太慢太脆时优先考虑。用 API 模拟用户流程 |
| **UI/E2E 测试** | 核心用户路径、页面跳转、关键交互、前后端真实集成 | 最接近真实用户、发布信心强 | 慢、脆、贵、维护成本高 | 少而精。只保留核心冒烟路径 |
| **验收测试** | 用户故事完成度、验收标准、业务价值交付 | 业务可读、连接产品/研发/测试 | 验收标准写得差会变空话 | 先关注业务契约，不默认等于 UI 自动化。可用 BDD/Gherkin |
| **生产巡检** | 部署后验证、核心链路巡检、蓝绿/灰度验证 | 发现测试环境发现不了的问题 | 必须非常谨慎、不能污染生产数据 | 只跑安全、只读、可回滚、低影响的核心路径 |

## 测试分类维度

### 按测试对象

| 分类 | 对应层 |
|---|---|
| 代码逻辑 | 单元测试 |
| 模块协作 | 组件测试 |
| 服务依赖 | 集成测试 |
| 接口行为 | API 测试 |
| 上下游一致性 | 契约测试 |
| 用户路径 | E2E 测试 |
| 业务验收 | 验收测试 |
| 生产健康 | 右移巡检 |

### 按测试目的

正确性、健壮性、兼容性、性能、可靠性、安全、可用性、回归、冒烟

### 按执行方式

手工测试、自动化测试、探索式测试、工具扫描、监控巡检

### 按阶段

- **左移**：需求、设计、开发、提交阶段
- **常规**：测试环境、集成环境、预发环境
- **右移**：灰度、生产、监控、巡检

## 分层决策树

对每一个测试点，按以下顺序决策：

```
1. 风险是否真实存在？
   └─ 否 → 不测
   └─ 是 ↓

2. 能用单元测试覆盖？
   └─ 能 → 单元测试（ROI 最优）
   └─ 不能 ↓

3. 能用 API / 集成测试覆盖？
   └─ 能 → API 或集成测试
   └─ 不能 ↓

4. 能用皮下测试覆盖？
   └─ 能 → 皮下测试
   └─ 不能 ↓

5. 必须 UI E2E？
   └─ 是 → UI E2E（最后手段）

6. 其他层是否已覆盖同一风险？
   └─ 是 → 不重复测
```

### 快速定位参考

| 测试点类型 | 优先层 | 原因 |
|---|---|---|
| 算法、计算、规则 | 单元测试 | 快、准、便宜 |
| 参数校验、边界值 | 单元 / API | 看逻辑位置 |
| 数据库读写 | 集成测试 | 需要真实依赖 |
| 第三方服务异常 | 集成测试 + Mock | 真实场景难构造 |
| REST/RPC 字段变化 | 契约测试 | 防上下游破坏 |
| 单接口正确性 | API 测试 | 稳定、易回归 |
| 多接口业务流 | API 流程 / 皮下测试 | 比 UI 更高 ROI |
| 用户核心路径 | UI E2E | 验证真实体验 |
| 页面布局 | 视觉测试 | UI 特有风险 |
| 生产服务健康 | 右移巡检 | 线上真实验证 |

## 3KU 原则

每个测试点必须通过三个检验：

1. **Useful（有效）**：这个测试点真的有价值吗？风险是否真实存在？
2. **Ultimate（最优层）**：它能不能放到 ROI 更高的层？能下沉就下沉。
3. **Unique（不重复）**：它有没有和其他层的测试重复覆盖同一件事？

> 不要问"这个场景能不能自动化"，先问"这个场景放在哪一层自动化最划算"。

## 自动化 ROI 评估

```
ROI = 运行次数 × 单次节省成本 / (开发成本 + 维护成本)
```

### 适合自动化的特征

稳定、高频、重复、核心、可断言、可维护、数据可控、失败可定位

### 不适合自动化的特征

一次性需求、频繁变化的页面、需求不稳定、断言不清楚、数据难准备、失败难定位、维护成本高

### 优先自动化的场景

冒烟测试、核心回归、关键接口、稳定业务规则、高频发布链路

## Mock 策略

### 适合 Mock

- 下游还没开发好
- 第三方服务不可控
- 异常场景难制造
- 真实调用成本高
- 真实环境不稳定
- 只想验证当前服务逻辑

### 不适合 Mock

- 需要验证真实集成
- 需要验证数据库脚本
- 需要验证协议兼容
- 需要验证真实网络和认证
- 需要验证完整生产链路

> Mock 解决可控性，真实集成解决真实性，两者都要有。

## 测试数据策略

### 数据分类

| 类别 | 说明 |
|---|---|
| 输入数据 | 传给接口或页面的参数 |
| 前置数据 | 用户、订单、商品、账户等业务实体 |
| 链路数据 | 上一个接口输出给下一个接口 |
| 环境数据 | 域名、token、租户、密钥 |
| 静态数据 | 枚举、字典、地区、分类 |

### 准备方式

| 方式 | 适用场景 |
|---|---|
| Out-of-box 预置 | 稳定基础数据 |
| On-the-fly 运行时造数 | 一次性、状态变化数据 |
| API 造数 | 优先推荐 |
| 数据库造数 | 谨慎使用，要版本管理 |
| Mock 数据 | 不可控依赖 |

> 测试数据准备、数据隔离、数据清理，要作为测试设计的一部分，不要藏在脚本里随便处理。
