# 编程的本质是翻译，而我们刚刚获得了一位新翻译 —— AI

> 我们从来都不是在"写程序"。我们只是在翻译。

## 一个有趣的起点

最近看到一个言论，大意是说：在用 AI 写代码（所谓 Vibe Coding）的时候，我们其实也不是在写程序，只是通过自然语言"翻译"成了程序。

乍一听像是废话。但仔细想想，这句话的力量在后半句——

**那么在以前，我们使用 C、Java、Python 的时候，我们也不是在写程序，也是在"翻译"。**

C 编译器把 C 翻译成汇编。汇编器把汇编翻译成机器码。Python 解释器把 Python 翻译成字节码。我们写的每一行代码，本质上都是在用某种翻译器能懂的语言，表达我们想让机器做的事。

AI 的出现只是换了一个翻译器。根本的范式并没有改变。

如果接受这个前提，那后面的推演就变得很有意思了。

## 第一章：翻译的谱系

把编程语言的历史画成一张图，你会看到一条清晰的线索：

编程语言抽象层谱系 —— 从机器码到自然语言


| 层级     | "语言"             | 翻译器                | 翻译目标          |
| ------ | ---------------- | ------------------ | ------------- |
| L0     | 机器码 (0/1)        | 人脑                 | CPU 指令        |
| L1     | 汇编 (MOV, ADD)    | Assembler          | 机器码           |
| L2     | C (`for`, `if`)  | Compiler           | 汇编            |
| L3     | Python, Java     | Interpreter/JVM    | C / 字节码       |
| L4     | SQL, HTML, React | Query Engine / 浏览器 | 执行计划 / DOM    |
| **L5** | **自然语言**         | **LLM**            | **L2-L4 的代码** |


每一次"升级"，本质都是同一件事：**抽象层的提升**。让人类用更接近自己思维方式的表达来描述意图，让翻译器去操心底层的事。

但第五层和前面四层有一个根本性的不同。

前四层的翻译器是**确定性**的。同一份 C 代码，用同一个编译器，永远编译出同样的二进制。这是工程的基石，也是程序员百年来的安全感来源。

第五层的翻译器是**概率性**的。同样一句话，GPT 今天给你写一个 for 循环，明天可能给你写一个 list comprehension。输出在语义上等价，但形式上不同。这不是 bug，这是 LLM 的本性——它是一个概率模型，不是一个确定性的编译器。

这意味着什么？

意味着 AI Coding 确实是编程语言谱系的延续——但它打破了一个存在了七十年的假设：**翻译过程必须是确定性的。**

有人会说这很危险。但回头看看，从汇编到 C 的时候，也有人说"编译器生成的代码不够优"；从 C 到 Java 的时候，也有人说"GC 不可控"；从 Java 到 Python 的时候，也有人说"动态类型不安全"。每一次都有人抱怨新翻译器不够精确——但每一次，表达力的提升都碾压了精确性的损失。

**AI Coding 不是编程的终结，而是高级语言演进谱系的最新一层。它是代理（Proxy），不是替代。**

## 第二章：代理，而非替代

这里有一个很重要的认知需要澄清。

很多讨论把 AI Coding 放在一个"AI vs 程序员"的对立框架里：AI 会不会取代程序员？什么时候取代？取代多少？

这个框架本身就是错的。

回到翻译的比喻。Python 有没有"取代" C？没有。Python 的底层运行时（CPython）就是 C 写的。Python 取代的不是 C 这门语言，而是**程序员直接用 C 处理高层业务逻辑的必要性**。底层系统编程、嵌入式、操作系统内核——C 依然是王者。

同理，AI Coding 取代的不是 Python、Go、TypeScript——它向下覆盖了这些语言，作为一个新的代理层存在。

AI Coding 作为代理层向下覆盖

你用自然语言告诉 AI 你要什么，AI 选择合适的语言来实现。有时候它生成 Python，有时候生成 Go，有时候生成 SQL，有时候生成 Shell 脚本。你不需要关心它选了哪门语言——就像写 Python 的人不需要关心 CPython 的 GC 用的是引用计数还是标记清除。

但这并不意味着底层语言消失了。恰恰相反，底层语言变得更重要了——因为 AI 生成的代码需要在真实的运行时上跑。Go 的并发模型、Rust 的所有权系统、TypeScript 的类型系统——这些不会因为有了 AI 就变得不重要。它们是 AI 生成代码的**质量下限**。

所以更准确的说法是：**AI Coding 是一层代理（Proxy Layer），它向下代理了 L2-L4 的所有语言，但并不替代它们。** 就像 Nginx 代理了后端服务但不替代它们一样。

这个认知改变了很多事情。它意味着：

- 学 Python/Go/Rust 依然有价值，因为它们是代理层背后的真实运行时
- "会写 prompt"不是终点，理解底层语言的人能写出更好的 prompt
- AI Coding 的上限取决于底层语言生态的成熟度——AI 不会凭空发明一个比 Rust 更安全的内存模型

## 第三章：当翻译变成编排

单次翻译（一个 prompt 生成一段代码）很快就会遇到天花板。

真实的软件工程不是"翻译一句话"。它是一个复杂的过程：先理解需求，再设计方案，然后分头实现前后端，写完做代码审查，审查不通过就打回修改，最后跑集成测试——这是一个有分支、有循环、有并行、有检查点的**流程**。

这就引出了一个问题：如果单次 AI 翻译是"一行代码"，那谁来写"整个程序"？

答案是**编排（Orchestration）**。

在传统编程中，我们有函数、模块、包来组织代码。在 AI Coding 的世界里，对应的概念是：

- **Skill** → 函数。一段封装好的、可复用的 AI 工作流程。它约束了 AI 的行为空间、绑定了可用的工具、定义了输入和输出。Skill 不是一句 prompt，它是 prompt + 工作流 + 工具链 + 校验规则的集合体。如果说 prompt 是"一行代码"，Skill 更像一个 **SDK/Framework**。
- **Agent** → 线程。一个独立的执行上下文，有自己的 prompt、Skill、权限边界。它在隔离的环境中执行任务，不会污染主线程的上下文。
- **Pipeline** → 程序。定义阶段顺序、并行策略、检查点（Gate），把多个 Skill 和 Agent 编排成一个完整的工作流。
- **Gate** → 断言 / 断点。流程中的人工检查点。AI 在这里暂停，把阶段性成果交给人类判断，收到确认后再继续。

这套类比不是凭空造的。它几乎完美地映射到了传统编程的概念体系：


| AI Coding 概念 | 传统编程等价物  | 作用       |
| ------------ | -------- | -------- |
| Prompt       | 一行代码     | 最小指令单元   |
| Skill        | 函数 / SDK | 封装可复用逻辑  |
| Agent        | 线程 / 进程  | 独立执行上下文  |
| Pipeline     | 程序 / 工作流 | 编排执行顺序   |
| Gate         | 断言 / 断点  | 暂停等待人类判断 |
| MCP (工具)     | 系统调用     | 连接外部能力   |


这张映射表的意义在于：**AI Coding 并没有发明新的编程范式，它只是在更高的抽象层上重现了我们已经熟悉的范式。**

## 第四章：Serverless 的味道

Skill 的形态让我想到了 Serverless。

传统程序：你写代码 → 编译 → 部署到服务器 → 启动进程 → 处理请求。你关心运行时、关心内存、关心并发、关心部署。

Skill "程序"：你写 Skill → AI 加载 → 按需触发 → 执行 → 返回结果。你不关心 LLM 内部的推理过程，不关心 token 怎么采样，不关心 attention 怎么计算——你只关心输入（触发条件）和输出（期望行为）。

这和 AWS Lambda 的理念如出一辙：**你只负责定义"做什么"，运行时（LLM）负责"怎么做"。**

但 Serverless 也有个教训值得吸取：当系统变复杂时，一堆散落的 Lambda 函数很快就变成了一团乱麻。AWS 的解决方案是 Step Functions——一个编排 Lambda 执行顺序的状态机。

Pipeline 在 AI Coding 中扮演的正是 Step Functions 的角色：把散落的 Skill 和 Agent 组织成有序的流程。

## 第五章：IDE 是 JVM

如果 AI Coding 是一门语言，Pipeline 是程序，那程序跑在什么上面？

**跑在 IDE 上。**

这个认知是反直觉的。我们习惯把 IDE 看作"开发工具"——一个文本编辑器加一些便利功能。但在 AI Coding 的语境下，IDE 的角色发生了根本性的转变。

Cursor、Claude Code、Codex——这些 IDE 都具备可编程的理论基础：

- **Hook 系统** → 系统调用。IDE 在特定时机（Agent 启动/停止、用户输入、Shell 执行前）触发回调，外部程序可以注入逻辑。
- **SubAgent / 子代理** → 线程 API。IDE 提供启动独立 Agent 的能力，每个 Agent 有自己的上下文、权限、工具集。
- **MCP 协议** → 设备驱动。标准化的接口协议，让 Agent 可以连接数据库、调用 API、操作浏览器。
- **文件系统访问** → 内存读写。Agent 通过读写文件来输入输出数据。

把这些拼在一起，IDE 不再是一个"编辑器"——它是一个**运行时环境**。Pipeline 是跑在这个运行时上的程序。Hook 是系统调用。SubAgent 是线程。

如果你愿意再推一步：**IDE 就是 JVM。**

Java 说"一次编写，到处运行"。Pipeline 应该也可以说"一次定义，所有 IDE 运行"。你用相同的 Pipeline 定义，在 Cursor 上通过 Task tool 启动 SubAgent，在 Claude Code 上通过 Agent tool 启动子代理，在 Codex 上通过原生的 SubAgent 系统执行。

当然，现实没有这么美好。每个 IDE 的"系统调用"接口不同——Cursor 有 `subagentStart/Stop` Hook，Claude Code 有 `PreToolUse/PostToolUse`，Codex 有 `PermissionRequest`。这就像不同操作系统的 syscall 表不一样。

解决方案也很熟悉：**加一层适配器。**

适配器负责把通用的 Pipeline 语义翻译成每个 IDE 的原生操作。这不就是 JVM 的 JNI（Java Native Interface）吗？或者更现代一点，这不就是 Docker 的 containerd 对不同 OS 的适配吗？

历史不会重复，但会押韵。

## 第六章：编排的表达力困境

到这里，自然而然会冒出一个想法：既然 Pipeline 是"程序"，那我们是不是应该设计一门"AI Pipeline 语言"？

这个问题并不新鲜。CI/CD 领域已经替我们趟过一遍了。

回顾 CI/CD 的演进：Makefile → Jenkins Groovy DSL → GitHub Actions YAML → Tekton → Dagger。每一代工具都在试图定义"如何描述一条流水线"。前几代倾向于自创一套配置语言，最终都遇到了同样的问题：用户的表达力需求（条件分支、变量、循环、错误处理）不断膨胀，迫使配置语言越来越像一门通用编程语言——但又永远比真正的编程语言差。

GitHub Actions 的 `${{ toJSON(needs.*.result) }}` 就是这条路走到中段的产物：它已经不是配置了，它是在 YAML 里硬写的蹩脚表达式，没有类型检查、没有调试器、没有社区。

这个规律几乎是宿命式的——**任何领域特定的配置语言，一旦用户开始需要逻辑，就会被推向通用语言的方向，却永远到不了。**

AI Pipeline 面临的是同一道题。当你的编排只有线性的"步骤 A → 步骤 B → 步骤 C"，任何格式都够用。但当你需要"如果 A 的结论是 X 就走简化流程，否则并行启动 B 和 C，完成后做一次人工审查"——你需要的就不再是配置了，你需要的是**编程**。

这个困境至今没有被完美解决。但方向已经隐约可见：与其在配置语言里重新发明轮子，不如让编程语言本身承担编排的职责，只在其上提供领域原语。这就像 React 没有发明新的模板语言，而是让 JavaScript 本身成为 UI 的描述工具。

具体的技术路径，这里暂且不展开。但这个困境本身值得记住，因为它揭示了一个更深的规律：**表达力的需求永远会追上任何受限的描述系统。** 这在编程语言的七十年历史里反复上演，在 AI Coding 的世界里也不会例外。

## 终章：我们在重新发现什么

让我把整条线索串起来。

```
命令式编程（汇编：告诉机器每一步怎么做）
  → 过程式编程（C：把步骤封装成函数）
    → 面向对象（Java：把数据和行为封装成对象）
      → 声明式编程（SQL/React：只说要什么，不说怎么做）
        → 意图式编程（AI Coding：用自然语言说意图，AI 翻译成程序）
```

每一次范式跃迁，都在做同一件事：**把"怎么做"变成"要什么"。**

汇编程序员需要管理寄存器。C 程序员不需要，但要管理内存。Java 程序员不需要管理内存，但要管理对象关系。SQL 用户不需要管理对象关系，但要知道表结构。AI Coding 的用户——理论上——只需要说清楚想要什么。

但每一次跃迁也都没有"消灭"上一层。写 SQL 的人仍然需要理解索引原理。写 React 的人仍然需要理解虚拟 DOM。用 AI Coding 的人仍然需要理解代码。

**抽象从来不是遮蔽，而是代理。** 每一层新的抽象都代理了下层的复杂性，但不消灭它。Nginx 代理了后端服务但不替代它们。Python 代理了 C 但不替代它。AI Coding 代理了所有高级语言但不替代它们。

这就是我从那个"有趣的言论"出发，走了一遍想明白的事情：

> **编程的本质是翻译，语言的本质是抽象。AI 不是取代了编程，而是在翻译的谱系上增加了新一层。Skill 是函数，Agent 是线程，Pipeline 是程序，IDE 是运行时。我们没有发明任何新东西，只是在一个更高的抽象层上，重新发现了编程本身的基本结构。**

至于那个最初的问题——"有没有可能做成一个 AI 语言"——答案可能比想象的更朴素：

这门"语言"不需要被发明。它已经存在了。

自然语言是它的语法。Skill 是它的标准库。Pipeline 是它的 `main()` 函数。IDE 是它的运行时。而 LLM——就是那个概率性的、不太精确的、但足够强大的编译器。

和历史上每一门高级语言一样，它不完美，但它把抽象层又往上推了一级。而这一级，恰好是人类语言本身。

我们用了七十年时间，从 0 和 1 开始，一步步把编程语言推向自然语言。现在到了。

接下来的问题不是"AI 会不会取代程序员"。

而是——**在这个新的抽象层上，好的"程序"长什么样？**
